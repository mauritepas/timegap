# timegap

**时间戳先归一化，再谈差多少。**

`timegap` 读取两个时间戳，输出它们之间的差值——天数、小时、分钟、秒，以及可直接给脚本用的原始秒数。
它不做时区推断，不解析自然语言时间，没支持的就直接报「不支持」。

- 零依赖，Python 3.10+ 标准库即可运行
- 单文件，`timegap.py` 拷走就能用
- 不联网、不写文件

## 为什么需要它

日志里是 `2026-10-20T10:00:00Z`，接口里是 `1760000000`，监控面板里又是毫秒。
三种表示混着算的时候，多半算出来的数是错的——而且错得很安静，没有任何报错。

更隐蔽的是时区：`2026-10-20 10:00:00` 这种没有时区信息的写法，
不同机器上按本地时区解释会得到不同结果，差值可能整整偏八小时。

`timegap` 的处理方式是明确的：

1. **先归一化**：所有输入统一转成 epoch 秒，差值只在这一个基准上算。
2. **时区缺失就明说**：没有时区标记的输入按 UTC 处理，并在输出里标注，不替用户猜。
3. **解析不了就报错**：时间类工具最怕静默出错，宁可退出码 2 也不给一个错数。

## 用法

```bash
# 两种写法算差值
python timegap.py --a "2026-10-20 10:00:00" --b "2026-10-21T12:30:00"

# ISO 带时区 vs epoch 秒
python timegap.py --a "2026-10-20T10:00:00Z" --b @1760000000

# 机器可读输出
python timegap.py --a "2026-10-20" --b "2026-10-21" --json

# 看看支持哪些格式
python timegap.py --list-formats
```

## 支持的格式

| 格式 | 例子 | 处理方式 |
|---|---|---|
| epoch 秒 | `1760000000` | 按位数自动判断秒/毫秒/微秒/纳秒 |
| ISO 8601 | `2026-10-20T10:00:00.123456` | 支持小数秒 |
| 带时区偏移 | `2026-10-20T10:00:00+08:00`、`...Z` | 转成对应偏移 |
| 斜杠分隔 | `2026/10/20 10:00:00` | 等同于 ISO |
| 仅日期 | `2026-10-20` | 按当日 `00:00:00` 处理 |
| `@` 前缀 | `@1760000000` | 等同于 epoch 写法，便于 shell 里避免被当成选项 |

没有时区信息的输入统一按 UTC 解释，并在输出的 `format` 字段里写明「无时区，按 UTC 处理」。
这是刻意选的：猜本地时区在服务器上几乎总是错的，而错得不出声。

## 已知局限

- **不处理自然语言时间**。「昨天下午三点」「三天前」这类输入会被拒绝，而不是尝试猜测。
- **不处理夏令时规则**。带偏移量的时间戳按固定偏移处理，不涉及任何时区数据库。
- **epoch 数值按位数判断单位**，位数在 9~10 之间视为秒、11~13 视为毫秒。若某个系统用秒但时间戳位数恰好落在边界，行为可能不符预期。
- **不做时长累加**。它只算两个时间点之间的差，不处理「工作日时长」「跨月计费」这类规则。
- **只比较两个时间点**，不做区间统计。

## 为什么还要做这个

现成的时间处理库功能更多，但大多数要求你先把输入整理成它认识的格式——
这一步往往才是真正花时间的地方。

`timegap` 反过来做：先把你手上那个看不懂的字符串接住，明确告诉你它被理解成了什么，
然后再给差值。宁可少支持几种格式，也不要在时区上给你一个错数。
